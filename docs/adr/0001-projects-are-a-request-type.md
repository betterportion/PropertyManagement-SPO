# Projects and capital projects are a type on maintenance requests, not a table

The main plan (section 5.5) said not to build a project entity. That judgment was about retrospective contractor history and stands for that; prospective work — projects SPO or a contractor initiates, and capital projects with competing bids and a signed contract — is a different question. We record it as a `type` on `maintenance_requests` (`request` / `project` / `capex`) rather than a separate table, because reusing the table gives projects status, room tagging, contractor links and threads for free, and gives one list per house instead of three. The cost is that cost and contract data now sits in a table resident accounts can read, so the type rule in `canReadMaintenanceRequest` — residents see type `request` and nothing else — lands in the same change as the column and is never derived from status or priority. Wishlist stays a priority, not a type: a wishlist capital project is a coherent thing.
